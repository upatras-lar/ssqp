SolverMode enum¶

enum SolverMode

Solver Mode The mode the solver uses for the system formulation, corresponding to the equality constraint of the NLP This can either be full dynamics, or a kinematics formulation Options:

  • Kinematics: The solver optimizes in a kinematic mode. This means there are no system dynamics. Instead, the generated controls correspond to velocities, while the state corresponds to the system configuration.
  • ForwardDynamics: The solver optimizes with a forward dynamics approach. The state corresponds to a stacked vector of the system configuration and velocity. The generated controls correspond to torques which, when applied over time to the system, generate the output trajectory.
  • InverseDynamics: The solver optimizes with an inverse dynamics approach. The state corresponds to a stacked vector of the system configuration and velocity. The generated controls correspond to accelerations. This simplifies the LQR formulation and can sometimes lead to more robust solutions. Inverse dynamics is used as a constraint, ensuring the torques producing the generated acceleration controls are within the required effort limits.
  • ReducedInverseDynamics: This mode is similar to the Inverse dynamics mode. In this mode, the floating base (if present) and/or some subset of the model's joints are unactuated. While regular Inverse mode enforces this via equality constraints, this mode instead enforces this implicitly through state propagation.
Value Description
Kinematics = 0
ForwardDynamics = 1
InverseDynamics = 2
ReducedInverseDynamics = 3

Model¶

#include <model/Model.hpp>

Defines an SSQP model An SSQP model object is a prerequisite to performing optimization using SSQP The model contains the following:

  • An optimization horizon, \(H\)
  • A cost function for each stage of the horizon, \(\ell_k(\boldsymbol{x}, \boldsymbol{u}) \in \mathcal{R}\), \(0 \leq k \leq H\)
  • Dynamics functions for each stage of the horizon, \(\boldsymbol{f}_k(\boldsymbol{x}, \boldsymbol{u}) \in \mathcal{R}^n\), \(0 \leq k \leq H\)
  • Constraint functions for each stage of the horizon, \(\boldsymbol{c}_k(\boldsymbol{x}, \boldsymbol{u}) \in \mathcal{R}^c\), \(0 \leq k \leq H\)

Of the above, all stage cost and dynamics functions must be defined, but constraints may be left empty.

Note that models optimize for \(H\) total steps while considering the initial state to be constant, whereas the initial controls can be altered. This means that there are \(H\) total controls ( \(\boldsymbol{u}_0\) to \(\boldsymbol{u}_{H-1}\)) and \(H + 1\) total states ( \(\boldsymbol{x}_0\) to \(\boldsymbol{x}_H\)), with \(\boldsymbol{x}_0\) being constant. At the terminal stage (stage \(H\)), there are no controls and, as such, stagewise functions must be appropriately defined to ignore them. Predefined functions all have constructors to account for this.

Models may be defined either by passing custom function implementations, or by using XML description files. Some constructors allow for defining a model using an XML file, but without passing the required cost functions. This is done to allow access to robot-related algorithms such as forward dynamics, which may be used to define model costs. Note that, if such constructors are used, the finalize method must be called before attempting to use the model for optimization. The user is responsible for either manually assigning all required costs, or passing them to the finalize method.

Structure¶

#include <model/Model.hpp>

Model Structure struct

Defines the structure of the SSQP model

A Structure object can be passed to the Model constructor to initialize a model with a structure only, without necessarily finalizing the model

Parameters:

  • urdf_path: Path to URDF describing robot (may be left empty if other description is used)
  • mjcf_path: Path to MJCF describing robot (may be left empty if other description is used)
  • free_flyer: Whether the model has a floating base (only relevant if initialized through XML)
  • from_preset: A URDF preset to build the model from (default Preset::None); mutually exclusive with urdf_path, mjcf_path and free_flyer
  • terrain: The ground terrain (default flat at z=0)
  • solver_mode: The solver mode to use (default ForwardDynamics)
  • integration: The integration scheme to use (default Semi-Implicit Euler)
  • ignore_innate_constraints: Whether to ignore innate constraints from the XML (i.e joint position, velocity and torque limits)
  • actuated_joints: Indices of the actuated joints (default empty -> all joints actuated)

Config¶

#include <model/Model.hpp>

Model Config struct

Defines the configuration of the SSQP model

A Config object needs to be passed when finalizing the model This can either be done by directly finalizing via the constructor, or by using the finalize method later on

Parameters:

  • costs: (size \(H\)) Vector of stage costs (added to existing costs)
  • stage_cost: Stage cost for all non-terminal stages (added to existing costs)
  • terminal_cost: Stage cost for terminal stage
  • constraints: (empty / size \(H + 1\)) Vector of stage constraints
  • dynamics: (empty -> XML dynamics / size 1 -> same dynamics for every stage / size \(H + 1\)) Vector of stage dynamics
  • custom_lower_position_bounds: Lower position bounds to use in place of the values read from the XML; default XML values are used if left empty; has no effect if innate constraints are ignored
  • custom_upper_position_bounds: Upper position bounds to use in place of the values read from the XML; default XML values are used if left empty; has no effect if innate constraints are ignored
  • custom_velocity_bounds: Velocity bounds to use in place of the values read from the XML; default XML values are used if left empty; has no effect if innate constraints are ignored
  • custom_torque_bounds: Torque bounds to use in place of the values read from the XML; default XML values are used if left empty; has no effect if innate constraints are ignored
  • init_states: (empty / size \(1\) / size \(H + 1\)) Vector of initial states (empty -> \(\boldsymbol{0}\) initial states / size \(1\) -> same initial state for every stage / size \(H + 1\) -> given sizes per stage)
  • init_controls: (empty / size \(1\) / size \(H\)) Vector of initial controls (empty -> \(\boldsymbol{0}\) initial controls / size \(1\) -> same initial controls for every stage / size \(H\) -> given controls per stage)

StageScope¶

#include <model/Model.hpp>

StageScope class

Kinematics and dynamics queries keep their results in caches, so that queries at the same point share a single computation Each stage has its own caches, so a stage's results are kept even with other stages' queries in between, and default caches serve queries outside of stages

While a StageScope exists, queries use stage k's caches, and the previously used caches are restored when it is destroyed

Results never depend on which cache is used, since each cache keeps the point its results are for; the scope only decides which results are kept for reuse Has no effect on models not loaded from an XML file

Model Structure Constructor

Initializes a model with the given structure

Input:

  • horizon: The time horizon to optimize over
  • dt: Time step per solver stage
  • structure: The structure of the problem

Note

This constructor does not finalize the model. The finalize method must be explicitly called before passing the model to a solver. If an unfinalized model is passed to a solver, the solver will attempt to finalize it with the default configuration.

Returns the actuated-joint torque vector implied by the inverse dynamics computation for the given state and controls, accounting for the given forces.

For InverseDynamics mode, this is the RNEA torque computed directly from the (full) acceleration control. For ReducedInverseDynamics mode, the full acceleration vector is reconstructed first (see getFullAccelerationVector), and only the actuated joints' torque is returned, since by construction the unactuated joints' torque is always zero

Input:

  • x: The model state
  • u: The model controls
  • forces: The linear forces the force part of u refers to, in order (see forces)
  • wrenches: The wrenches the force part of u refers to, after the linear forces (see wrenches)

Note: XML-based function Note: Assumes the model is in InverseDynamics or ReducedInverseDynamics mode
