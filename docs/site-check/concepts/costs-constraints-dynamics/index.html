Costs, Constraints & Dynamics¶

Costs, dynamics and constraints are all stagewise functions: they evaluate at a single stage's \((\boldsymbol{x}, \boldsymbol{u})\) and provide the derivatives SSQP needs to quadratize the cost and linearize the dynamics/constraints at each iteration. StageCost, StageDynamics and StageConstraints all extend a common Function interface (evaluate, output_size, names), then add their own gradient/Hessian requirements.

You can implement any of these from scratch in Python (as in the Quickstart) or C++, or use one of the predefined implementations that ship with SSQP, listed below and fully documented in the Python API reference.

Inputs and outputs in C++¶

In Python, every method returns its outputs. In C++, they are written into arguments instead, so that the solver can reuse its storage between calls:

  • The inputs are ConstVecXRef (Eigen::Ref<const VecX>), so blocks of larger vectors are passed without copies.
  • evaluate(x, u, out), gradient(x, u, dX, dU), the cost hessian_*, the hessprod_*, constraint right_minus and dynamics state_right_plus/state_right_minus set their outputs, resizing them as needed. A cost's evaluate writes a vector of size 1.
  • evaluate_into, right_minus_into, state_right_plus_into and state_right_minus_into write into an output that is already sized, such as a block of a larger vector. add_gradient, add_hessian_* and add_hessprod_* add to outputs that are already sized.

A custom function only needs the first set: the base classes implement the second through it. The predefined functions do the opposite, deriving from PredefinedStageCost/PredefinedStageConstraints, which implement the first set through the second.

Costs¶

StageCost (\(\ell_k(\boldsymbol{x}, \boldsymbol{u}) \in \mathcal{R}\), so output_size() is always 1) requires:

  • evaluate(x, u): the scalar cost
  • gradient(x, u): \(\nabla_x \ell_k\) and \(\nabla_u \ell_k\)
  • hessian_xx(x, u), hessian_xu(x, u), hessian_uu(x, u): the cost Hessian blocks

Costs can be named, enabled/disabled at runtime (set_enabled/enabled, though a stage always keeps at least one cost, so disabling every cost on a stage has no effect), and multiple costs can be added to the same stage via Model.addCost / Model.addRunningCost.

Predefined costs¶

ssqpy.model.costs (ssqp::model::stagewise in C++) ships a library of squared-error costs for common OCP objectives, all built on Pinocchio kinematics for XML-based models:

SquaredJointAngleCost, SquaredJointVelocityCost, SquaredControlCost, SquaredIDTorqueCost, SquaredForceCost, SquaredConfigurationErrorCost, FloatingBaseSquaredTranslationErrorCost, FloatingBaseSquaredRotationErrorCost, FloatingBaseSquaredPoseErrorCost, FloatingBaseSquaredVelocityErrorCost, FrameSquaredTranslationErrorCost, FrameSquaredTerrainHeightErrorCost, FrameSquaredRotationErrorCost, FrameSquaredPoseErrorCost, FrameSquaredVelocityErrorCost, CenterOfMassTrackingCost, FramesInverseSquaredDistanceCost.

See ssqpy.model.costs for constructor arguments and details for each.

Predefined costs and constraints refer to the model they are built with rather than copying it, so they always see its current forces and terrain. In C++, the model must outlive them, and a Model cannot be copied. In Python, each one keeps its model alive.

Dynamics¶

StageDynamics (\(\boldsymbol{f}_k(\boldsymbol{x}, \boldsymbol{u}) \in \mathcal{R}^{n_x}\)) requires:

  • state_size(), control_size(): dimensions of \(\boldsymbol{x}\) and \(\boldsymbol{u}\)
  • evaluate(x, u): the next state
  • gradient(x, u): \(\nabla_x \boldsymbol{f}_k\), \(\nabla_u \boldsymbol{f}_k\)
  • hessprod_xx, hessprod_xu, hessprod_uu: vector-Hessian products against the Lagrange multiplier \(\boldsymbol{\lambda}_k\) (used instead of raw Hessians, since \(n_x\) can be large)

Dynamics also define the manifold structure of the state through state_right_plus/state_right_minus (and state_diff_size, when the tangent space differs in size from the state itself). For a Euclidean state these default to plain vector addition/subtraction; for states that include e.g. a floating-base orientation (a Lie group element), they implement the appropriate manifold operators. Predefined, XML-based dynamics already handle this correctly for the selected SolverMode and Integration.

Manifold-valued states¶

Not every model's state lives in a flat Euclidean space \(\mathcal{R}^{n_x}\). A floating-base robot's orientation, for example, is an element of the Lie group \(SO(3)\) (or its full pose, \(SE(3)\)), not a vector: adding two orientations, or taking their plain difference, isn't a well-defined operation. Rather than requiring \(\boldsymbol{x} \in \mathcal{R}^{n_x}\), SSQP treats a dynamics function's domain as an arbitrary composite manifold: a state can combine one or more manifold-valued segments with one or more ordinary Euclidean segments, and every place SSQP would otherwise use vector addition/subtraction instead goes through two operators:

  • \(\boldsymbol{x} \oplus \boldsymbol{dx}\) (state_right_plus): retracts a tangent-space update \(\boldsymbol{dx}\) onto the manifold at \(\boldsymbol{x}\), producing a new state.
  • \(\boldsymbol{x}_1 \ominus \boldsymbol{x}_2\) (state_right_minus): the tangent-space displacement between two states, i.e. their local, chart-consistent difference.

For a purely Euclidean state, these reduce to plain vector addition/subtraction, and state_diff_size() (the tangent space dimension \(n_{dx}\)) defaults to state_size() (\(n_x\)). For a manifold-valued segment, \(n_{dx}\) can differ from \(n_x\): a quaternion-parameterized \(SO(3)\) orientation, for instance, contributes 4 parameters to \(n_x\) but only 3 degrees of freedom to \(n_{dx}\). SSQP linearizes, integrates and reports convergence norms in the tangent space, never in the raw parameterization, so the gradients/Hessians returned by gradient/hessprod_* are always sized against state_diff_size() (\(n_{dx} \times n_{dx}\) or \(n_{dx} \times n_u\)), not state_size().

XML-based (Pinocchio-backed) models handle all of this automatically: a free_flyer=True model's floating-base pose is represented and integrated as its native \(SE(3)\)/quaternion manifold element, and the predefined costs/constraints that touch floating-base or frame poses (e.g. FloatingBaseSquaredPoseErrorCost, FrameTranslationBound) use the corresponding Lie-group log/exp maps internally, consistent with the selected Integration scheme. Custom dynamics only need to implement state_right_plus/state_right_minus (and state_diff_size, if it differs from state_size) to opt into the same treatment for their own manifold-valued states.

Constraints¶

StageConstraints (\(\boldsymbol{c}_k(\boldsymbol{x}, \boldsymbol{u}) \geq \boldsymbol{0}\), or bounded via lower_bound()/upper_bound()) mirrors StageDynamics' derivative interface (gradient and hessprod_xx, hessprod_xu, hessprod_uu against a multiplier \(\boldsymbol{\mu}_k\)) for an arbitrary output size, and adds:

  • lower_bound() / upper_bound(): per-element bounds (defaults to \([0, \infty)\), i.e. an inequality \(\geq 0\); pass equal bounds for an equality constraint)
  • required_forces() / force_frame(i): for constraints that involve external contact forces (see Contacts and forces in Model)
  • state_only_rows() (optional): the rows of the difference vector that depend only on \(\boldsymbol{x}\). The initial state fixes them at stage 0, so SSQP leaves them out there instead of letting a violated one make the QP infeasible
  • box_rows() (optional): the rows whose gradient is always \(+1\) on a single state or control entry, as BoxRow(row, index, is_control), which HPIPM handles as simple bounds instead of general constraints

In C++, state_only_rows and box_rows overwrite a std::vector passed to them instead of returning one.

Predefined constraints¶

ssqpy.model.constraints provides: JointAngleConstraint, JointVelocityConstraint, JointControlConstraint, FloatingBaseTranslationBound, FloatingBaseRotationBound, FloatingBasePoseBound, FloatingBaseLinearVelocityBound, FloatingBaseAngularVelocityBound, FrameTranslationBound, FrameTerrainHeightBound, FrameRotationBound, FramePoseBound, FrameLinearVelocityBound, FrameAngularVelocityBound, CenterOfMassBound. The C++ library additionally defines ContactConstraint directly, which Model.addContactConstraint constructs and wires up for you (friction cone + non-penetration against the model's terrain + no-slip zero velocity, which no_slip=False turns off).

See ssqpy.model.constraints for constructor arguments and details for each.

Reference frames¶

Predefined costs and constraints on a position or a velocity take a reference_frame, either as a constructor argument or through set_reference_frame. It selects the axes that a cost's error, weights and desired value, or a constraint's bounds, are expressed along. Only the axes change: positions keep the world origin. A world vector \(\boldsymbol{v}\) is expressed along axes with rotation \(R\) (whose columns are the axes in world coordinates) as \(R^\top \boldsymbol{v}\).

Option Axes
ReferenceFrame.World The world axes
ReferenceFrame.Local The axes of the frame the cost or constraint acts on, moving with it
ReferenceFrame.Base The axes of the model's floating base, moving with it. On floating base terms this is the same as Local
ReferenceFrame(rotation) Fixed axes given by a rotation matrix. A 3x3 array converts to these implicitly
ReferenceFrame.yaw(angle) Fixed axes rotated about the world \(z\) axis
ReferenceFrame.normal(normal, yaw=0.0) Fixed axes with \(z\) along a surface normal and \(x\) along the horizontal direction at angle yaw from the world \(x\) axis, projected onto the surface

In C++, the same options are ReferenceFrame::World, ReferenceFrame::Local, ReferenceFrame::Base, ReferenceFrame(rotation), ReferenceFrame::yaw(angle) and ReferenceFrame::normal(normal, yaw), in ssqp::model::stagewise::predefined.

Each term supports the options that make sense for it. Positions, a frame's linear velocity bound and its velocity cost default to the world axes, while floating base velocities, which the state holds in the base frame, and a frame's angular velocity bound default to Local:

Term Options Default
FrameTranslationBound, FrameSquaredTranslationErrorCost World, Fixed, Local, Base World
FloatingBaseTranslationBound, FloatingBaseSquaredTranslationErrorCost World, Fixed, Local (= Base) World
FloatingBaseLinearVelocityBound, FloatingBaseAngularVelocityBound, FloatingBaseSquaredVelocityErrorCost Local (= Base, the base frame), World, Fixed Local
FrameLinearVelocityBound, FrameSquaredVelocityErrorCost World, Local, Fixed, Base World
FrameAngularVelocityBound Local, World, Fixed, Base Local
CenterOfMassBound, CenterOfMassTrackingCost, FramesInverseSquaredDistanceCost World, Fixed, Base World

Rotation and pose costs and bounds are not in the list: they already measure their error along their reference's axes, so choosing the reference rotation chooses the axes. For FramesInverseSquaredDistanceCost, the reference frame sets the axes the distance scale applies along.

Passing an option a term does not support raises ValueError (std::invalid_argument in C++), as does Base on a model without a floating base, or a rotation that is not orthonormal with determinant 1.

Bound centers¶

The position bounds (FrameTranslationBound, FloatingBaseTranslationBound and CenterOfMassBound) also take a center \(\boldsymbol{c}\), through the constructor or set_center, which moves the bounds' origin whatever the reference frame:

\[ \boldsymbol{b}_l \leq R^\top (\boldsymbol{p} - \boldsymbol{c}) \leq \boldsymbol{b}_u \]

For example, a box around a foothold, aligned with the robot's yaw and updated at each MPC step:

import numpy as np
from ssqpy.model import ReferenceFrame, constraints, costs

box = constraints.FrameTranslationBound(
    model,
    "FL_foot",
    lb=np.array([-0.05, -0.03, -np.inf]),
    ub=np.array([0.05, 0.03, np.inf]),
    reference_frame=ReferenceFrame.yaw(robot_yaw),
    center=foothold,
)

# Later, for a new plan
box.set_reference_frame(ReferenceFrame.yaw(new_robot_yaw))
box.set_center(new_foothold)

Similarly, a commanded base velocity given in world axes can be tracked directly, rather than converted to the base frame first:

costs.FloatingBaseSquaredVelocityErrorCost(
    model, v_command, weight, reference_frame=ReferenceFrame.World
)

Moving axes¶

Local and Base axes depend on the state, so the derivatives of these terms include how the axes turn with the frame or the base. On a bound, this gives the solver a second way to satisfy it: turning the frame or the base instead of moving the point. With Base axes on a foot box, for example, the plan may yaw or pitch the body to fit the foot inside. That is the intended behaviour for bounds meant relative to the body. When it is not, use fixed axes, such as ReferenceFrame.yaw with the planned yaw of each stage.

Innate (XML-derived) constraints¶

When a model is built from a URDF/MJCF file, joint position, velocity and torque limits declared in the XML are added automatically as constraints unless ignore_innate_constraints=True is passed to the Model constructor. finalize's custom_lower_position_bounds, custom_upper_position_bounds, custom_velocity_bounds and custom_torque_bounds arguments override the XML-derived values in place.
